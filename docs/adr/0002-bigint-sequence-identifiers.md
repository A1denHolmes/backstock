# 0002. Identifiers: bigint with sequences

## Status

Accepted

## Date

2026-09-26

## Context

Every entity needs a primary key. The choice affects index size, insert performance, how IDs look in URLs and
whether Hibernate can batch inserts.

The application uses a single PostgreSQL database and does not generate IDs on the client or merge data from other
sources.

## Options considered

**UUID v4.** 16 bytes, globally unique and not guessable. Random values land in random places of the B-tree index,
which makes inserts slower and indexes larger.

**UUID v7.** Time-ordered, so inserts are append-only like with a sequence. Still twice the size of `bigint` and
harder to read in logs and URLs. Global uniqueness brings nothing to a single-database application.

**bigint with IDENTITY.** The simplest mapping. The ID is only known after the insert, so Hibernate has to execute
each insert immediately and cannot batch them.

**bigint with SEQUENCE.** The ID is fetched from a sequence before the insert. With the pooled optimizer Hibernate
reserves a block of values per call to the sequence, and inserts can be batched.

## Decision

We will use `bigint` primary keys generated by PostgreSQL sequences through `GenerationType.SEQUENCE`.

Each table has its own sequence. The allocation size is 50, and every sequence is created with `INCREMENT BY 50`.

## Consequences

- Keys take 8 bytes and indexes stay compact.
- Inserts can be batched once JDBC batching is enabled.
- The sequence increment in migrations and the allocation size in mappings must stay equal.
- IDs have gaps: unused values of a reserved block are lost on restart.
- IDs are sequential and easy to guess, so access to a resource by ID always goes through an ownership check.
